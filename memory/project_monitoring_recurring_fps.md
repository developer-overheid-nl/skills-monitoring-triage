## Monitoring approach (as of 2026-04-07)

The monitoring scripts now use `extract_visible_text()` instead of `normalize_html()`. This function extracts only visible body text (stripping scripts, styles, noscript, HTML tags) and hashes that. This eliminates all CMS-specific false positives (Drupal, Liferay, Next.js, etc.) in one go — no more per-pattern regex maintenance needed.

The old `normalize_html()` with ~100 lines of CMS-specific regexes was removed in PR #156 (geo), #129 (internet), #363 (standaarden) on 2026-04-07.

**Important:** After any change to `extract_visible_text()`, the next monitoring run will trigger a bulk hash reset (all URLs flagged as "changed"). This happened on 2026-04-08 (137 issues, all closed as bulk reset). Recognize this pattern: many/all issues created on the same day = hash reset, close in bulk.

## Broken-link false positives (monitoring-links.yml / lychee)

These come from the links workflow, not the content workflow, and carry the `monitoring,broken-link` label.

| Host / pattern | Repo/Skill | Why it triggers | Action |
|-----|-----------|----------------|--------|
| `docs.geostandaarden.nl/*` reported as `[TIMEOUT]` (not ERROR/404) | skills-geo | The host is intermittently slow under lychee's default timeout; a whole batch of geostandaarden URLs times out together in one run, then all return 200 within ~0.2s on a manual re-check. This is a transient host-speed FP, the links are fine. | Verify with `curl -s -o /dev/null -w "%{http_code} %{time_total}s" -L <url>` on a few of the timed-out URLs. If they 200 quickly, do NOT close manually and do NOT edit links: the workflow auto-closes the rolling issue on the next 06:00 run once the host responds in time. Confirmed 2026-06-20 (skills-geo #262: all 7 timed-out docs.geostandaarden.nl URLs returned 200 in ~0.2s). Only treat as real if lychee reports `[ERROR]`/4xx, or the URL is genuinely unreachable on re-check. |

| `gitdocumentatie.logius.nl/*` reported as `[ERROR] Network error: received fatal alert: UnrecognisedName` | skills-standaarden | The host serves a certificate with CN `logius.nl` that does not cover the hostname, and rejects SNI for `gitdocumentatie.logius.nl`. Lychee uses rustls and is stricter than curl, so it aborts; curl and browsers accept the connection and the links work fine. Hits all ~33 gitdocumentatie URLs at once, which are the DEF-publication links the skills lean on most. | Verify with `curl -s -o /dev/null -w "%{http_code}" -L <url>` (all return 200) and confirm the cert with `echo \| openssl s_client -connect gitdocumentatie.logius.nl:443 -servername gitdocumentatie.logius.nl`. **Why:** Recognizing these patterns early saves investigation time during daily triage.

**How to apply:** When triaging, for frequently-changing URLs, verify the skill doesn't reproduce specific content from the page, then close. This table is the **single source of truth** for the per-URL recurring-FP log; the `monitoring-triage` skill no longer duplicates it (it keeps only two archetype rules + a short exception list). When you confirm a new recurring pattern during triage, add the row here, not to the skill. Most rows reduce to one of two archetypes: **Rule A** (HTTP body-hash drift on a reference page → close if hashes stable over 3 fetches and the skill only links as reference) or **Rule B** (pure-beheer commit in an upstream `logius-standaarden/*` or `Geonovum/*` repo → close after reading the commits). The genuine exceptions that need different handling are ogc-checker new tags (version-pin bump), Internet.nl releases, st-saml-spec version publications, and logboek-extensie-lezen method changes.
