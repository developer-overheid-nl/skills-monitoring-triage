## Monitoring approach (as of 2026-04-07)

The monitoring scripts now use `extract_visible_text()` instead of `normalize_html()`. This function extracts only visible body text (stripping scripts, styles, noscript, HTML tags) and hashes that. This eliminates all CMS-specific false positives (Drupal, Liferay, Next.js, etc.) in one go, no more per-pattern regex maintenance needed.

The old `normalize_html()` with ~100 lines of CMS-specific regexes was removed in PR #156 (geo), #129 (internet), #363 (standaarden) on 2026-04-07.

**Important:** After any change to `extract_visible_text()`, the next monitoring run will trigger a bulk hash reset (all URLs flagged as "changed"). This happened on 2026-04-08 (137 issues, all closed as bulk reset). Recognize this pattern: many/all issues created on the same day = hash reset, close in bulk.

**Why:** Recognizing these patterns early saves investigation time during daily triage.

**How to apply:** When triaging, for frequently-changing URLs, verify the skill doesn't reproduce specific content from the page, then close. This table is the **single source of truth** for the per-URL recurring-FP log; the `monitoring-triage` skill no longer duplicates it (it keeps only two archetype rules + a short exception list). When you confirm a new recurring pattern during triage, add the row here, not to the skill. Most rows reduce to one of two archetypes: **Rule A** (HTTP body-hash drift on a reference page → close if hashes stable over 3 fetches and the skill only links as reference) or **Rule B** (pure-beheer commit in an upstream `logius-standaarden/*` or `Geonovum/*` repo → close after reading the commits). The genuine exceptions that need different handling are ogc-checker new tags (version-pin bump), Internet.nl releases, st-saml-spec version publications, and logboek-extensie-lezen method changes.
